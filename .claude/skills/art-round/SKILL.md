# 美術輪

狀態美術第二版、第三版都是整組做完才給使用者看，結果整組否決（HANDOFF N、WORKLOG §2 BR），白白耗掉 Codex 額度。這份流程的重點是：**先讓一個代表素材通過，才做其他的**。做法改寫自 awesome-gamedev-agent-skills 的 `create-game-assets`（Apache-2.0）。

## 1. 先盤點，不從零發想
- 讀 `docs/ART_STYLE_BIBLE.md`、`docs/ART_SPEC.md`（§10 可讀性、§11 驗收），以及 HANDOFF 裡這類素材被否決過的方向和理由。
- 使用者的既定偏好（memory）：狀態表現在模型本身，不在單位上堆圖示；奧義是半透明發光的能量構造體；現在的素材就是正式版；UI 標題不用中文。
- 找出要取代的現行素材，在截圖上量它的實際高度（px），新素材的目標尺寸以這個為準，不用猜的。

## 2. 寫簡報（放進該輪提示詞的 DOM）
每一軸都寫看得見的性質，不寫「好看」「精緻」「有質感」；也不用在世藝術家的名字當風格定義。

| 軸 | 要定下來的事 |
| :-- | :-- |
| 輪廓 | 原尺寸下一定要認得出的部位；哪些部位不能和身體糊成一塊 |
| 明度 | 轉成灰階後，在森林、岩漿、冰原上都還分得出來嗎 |
| 色彩角色 | 陣營色、危險、增益、中性各用哪些色票（寫色碼） |
| 邊緣與材質 | 描邊粗細與顏色、平塗或漸層、發光的用量 |
| 光向 | 和現有烘焙單位一致 |
| 細節密度 | 細節集中在哪裡；原尺寸下哪些會消失（消失的就不要畫） |
| 動態 | 移動、轉身時哪些部位可以變形，可以變形多少 |

技術框架：桌機與手機（393×852、縮放 0.68）的實際高度、錨點（腳底中心）、透明背景（用純綠 `#00FF00` 去背，見 BIBLE §6）、張數與方向、效能限制（沿用該類素材的現行限制）。

## 3. 代表素材關卡（必過）
1. 先只做**一個**代表素材，2～3 個變體就好。
2. 做對照板（§5），主代理先自己用原尺寸看一遍，看不出差別的變體直接淘汰。
3. 把對照板給使用者選。**核准之前不做其他素材**；派 Codex 時也把這一步寫成停下條件：「交出代表素材的對照板後結束，不做整組」。
4. 使用者把選擇交給主代理時，挑最強的一個，並把理由寫下來，不卡住流程。
5. 核准的檔案就是這一輪的**基準圖**，路徑寫進提示詞與 HANDOFF。

## 4. 成組量產
- 每次都拿基準圖當參考圖或編輯來源，色票、視角、比例、光向、描邊固定不動。
- 一次一小批（同一個家族），每一版只改一個變數。「整體再好一點」這種廣泛修改最容易跑掉。
- **風格跑掉的訊號**：身高或頭身比改變、描邊粗細或顏色改變、高光暗示不同光向、色票多出相近的髒色、後面的版本雜訊越來越密、視角或投影改變、腳底接地點和影子位置亂跳。
- 一旦跑掉，就回基準圖重做受限的修改，不要在跑掉的版本上繼續改（它會變成意外的新基準）。
- 單獨看很漂亮、但不屬於這套視覺系統的，一律退回。

## 5. 對照板（每一版都做，用原尺寸判斷）
- **靜態圖**（概念稿、去背後的素材）：
  `python tools/assets/art-board.py <候選.png ...> --bg <截圖 ...> --height <實際高度px> --out tools/ui-e2e/out/<名稱>.png [--at X,Y]`
  每個候選一列：每張背景一格（貼成實際大小）、第一張背景的灰階、放大檢查。背景可以用 `tools/ui-e2e/baseline/fidelity/` 的五種地形和 `battle_frozen`，手機截圖另外擷取。退出碼 1 代表有候選沒有透明像素（背景被烤進去了）。
- **執行時畫的**（狀態、特效、程式繪製）：在遊戲裡擷取同樣的欄位：桌機、手機原尺寸、20 人混戰、最難辨識的背景（岩漿、冰原）、灰階，**加上移動和轉身的連續畫面**（METHODOLOGY §4.10）。
- 判斷順序：原尺寸 → 放大 → 混戰。只有放大才看得出來的，算不及格。
- 對照板要附「現行版本」那一列，讓使用者直接比較新舊。

## 6. 收尾
- 每個新檔記進 `docs/ASSET_LEDGER.md`（來源、模型或作者、授權、日期、提示摘要）。
- 核准與否決都寫下來：基準圖路徑、否決過的方向和理由（像 HANDOFF N 那樣），讓下一輪不重走。
- 原型與對照板放在 repo 外的 `C:\Git\_wt_<topic>`，或不進版控的 `tools/ui-e2e/out/`。
- 接進圖集或渲染器（`public/assets/`、`engine/`、`data/vfx/`、圖集載入）就是渲染工作：同一時間只開一條，走 `render-verify`。
- 回報的驗證要分級（`agent-prompt` 的回報格式）：使用者看過、在實機上看過，都和主代理在桌機截圖上看過分開寫。
