# PLAY 操控手感：實測、MOBA／RTS 對照、修法方向（研究備忘，2026-11-25）

> 主代理 Opus。使用者 11-25：「控制不貼手，反應會延遲」「技能像是要在範圍中才可以進」「研究 MOBA 和 RTS 的控制傳導」「各種遊戲模式都是回合切片和連接」。
> 本檔只有研究與提案，沒有改 `engine/`。修法要動 ADR 0022 的指令節點，屬架構決策，使用者同意後另寫 ADR 再動手。

## 1. 結論

- **架構沒錯，錯在規則**：輸入 → 指令佇列 → 固定步長模擬這條傳導鏈很快（主角閒著時 1～3 tick，17～50 ms）。慢的是 ADR 0022 決定「玩家指令直接呼叫既有 AI 節點」之後，AI 為了不抖動、不浪費而設的規則也套到了玩家身上。
- **四個來源**（§2 有數字）：
  1. 普攻前搖鎖住新指令：反擊姿態下主角常在普攻前搖，這時下移動要等前搖走完，中位數 0.48 秒。
  2. 走路中改目的地要等 0.25 秒：AI 防抖的換路間隔 `PATH_RULES.REPATH_MIN_S` 也套在玩家身上。
  3. 施放指令放不出來時原地乾等，不普攻：冷卻中等到冷卻完；魔力不足永遠等不到（魔力只靠出招累積，乾等就不會漲）；自身技身邊沒敵人時，AI 的「值不值得放」判斷擋住，一直等。**這就是「要在範圍中才能放技能」的感覺。**
  4. 輸入層：指令在放開滑鼠時才送；按下後游標漂移超過 8 px（觸控 18 px）就變成拖鏡頭，指令整個不見。
- **對使用者的架構問題**：時間切片這一層已經具備，回合、半回合、即時、掛機都能接在上面；但回合與半回合還缺兩樣東西，它們不是切片本身（§4）。

## 2. 實測（RTX 4070、無頭 Edge，PLAY 模式，單位是模擬秒）

探針不進版控：`tools/ui-e2e/out/input-latency3.mjs`（A、B 兩節）、`input-latency2.mjs`（C 節）。指令經 `engine.bus` 送 `UI_COMMAND`，量的是指令層以下；C 節用真實滑鼠。

### A. 移動指令（`node tools/ui-e2e/out/input-latency3.mjs 10`，每種 10 筆，戰士）

| 下令當下主角在做什麼 | 路徑換成新目的地 | 開始往新目的地移動 | 原因 |
| :-- | :-- | :-- | :-- |
| 閒著（站定） | 0.017（10 筆都是） | 中位數 0.05，最大 0.28 | 正常：指令在下一個 tick 開頭套用（ADR 0015） |
| 普攻前搖中 | 中位數 0.48，0.28～0.50 | 中位數 0.43 | `OrderMove`：「正在前搖：放完再走」；前搖剩餘中位數 0.47，和延遲一致 |
| 走路中改向 | 中位數 0.23，最大 0.25 | 中位數 0.25 | `MovementSystem.moveAgentToHex`：目的地變了，0.25 秒內先沿舊路走（`REPATH_MIN_S`） |

普攻前搖 0.2～0.8 秒（50 招中位數 0.5），冷卻約 1 秒，所以反擊姿態的主角大約一半時間卡在前搖。

### B. 施放指令（四個職業各開一場，每種情況 1～2 筆）

| 情況 | 結果 | 原因 |
| :-- | :-- | :-- |
| 射程內、可放 | 前搖時間到就放出（0.2～0.8） | 正常 |
| 射程外、可放 | 先走進射程再放（1.8～2.0） | 正常，和 LoL 點射程外會走過去一樣 |
| 冷卻中 | 指令收下，主角**站著不動、不普攻**直到冷卻完（3.55） | `OrderCast` 放不了就 `standBy` |
| 魔力不足 | 指令收下，主角**站著不動，6 秒內都沒放出**（3 筆）；遊俠還在等待中被打掉魔力 | 同上；魔力只從出招回（`commitSkill` 的 `gain`），乾站永遠等不到 |
| 自身技（射程 0）、身邊沒敵人 | 指令收下，**站著不動，6 秒內都沒放出**（2 筆） | 沒指定目標時走 AI 的 `FindOptimalTarget`，身邊沒敵人就判定不值得放 |

HUD 的技能鈕（`PlayHUD.pressSlot`）不看冷卻與魔力，按了就進瞄準或直接下令；檢視資料裡其實已有不能放的原因（`views/play.ts` 的 `activationBlock`）。

### C. 真實滑鼠點地面（`input-latency2.mjs`，每種漂移 2 筆）

| 按下到放開之間游標漂移 | 0 px | 4 px | 7 px | 10 px |
| :-- | :-- | :-- | :-- | :-- |
| 移動指令送出 | 1／2 | 2／2 | 2／2 | 0／2 |

10 px 兩次都變成拖鏡頭，指令不見（門檻 `GAME_INPUT_PARAM.DRAG_DRIFT_MOUSE_PX` 8、觸控 `DRAG_DRIFT_TOUCH_PX` 18）。0 px 那一次沒送出，原因沒查（可能點到單位或障礙物），樣本小。另外指令在 `pointerup` 才送，按住多久就多延遲多久，探針量不到這段。

## 3. MOBA／RTS 怎麼做，和我們的差距

| 項目 | MOBA／RTS 常見做法 | 我們現在 |
| :-- | :-- | :-- |
| 新指令打斷自己的動作 | Dota 2：出手點之後第一個移動指令會取消後搖（Liquipedia，經搜尋摘要）；按停止可中止施法 | 前搖中一律等放完，普攻也一樣 |
| 新指令換目的地 | 立刻換路 | 玩家也套 AI 的 0.25 秒換路間隔 |
| 射程外施放 | LoL：依技能，會走進射程再放、在最大射程放、或不放（LoL Wiki Targeting） | 走進射程再放（一致） |
| 冷卻中、魔力不足 | 不收指令，給提示（按鈕變暗、音效） | 收下指令，主角乾站等 |
| 施法中下的指令 | LoL：施法時間內下的指令會緩衝，施法完再執行（LoL Wiki Cast bar） | 新指令直接取代舊指令；前搖中的新指令等前搖完（效果接近緩衝，但沒有回饋） |
| 選目標步驟 | Dota 2 的 Quick Cast：按技能鍵就對游標下的目標放，不必再點一次（設定可逐招選） | 一律「按鍵 → 進瞄準 → 再點」 |
| 下令的時機與回饋 | 按下就送；RTS 的單位「收到」回應立刻播，延遲藏在後面（AoE 的 lockstep 討論） | 放開才送；漂移超過門檻就變拖鏡頭 |

來源：[LoL Wiki：Targeting](https://wiki.leagueoflegends.com/en-us/Targeting)、[LoL Wiki：Cast bar](https://wiki.leagueoflegends.com/en-us/Cast_bar)、[Liquipedia：Cast Animation](https://liquipedia.net/dota2/Cast_backswing)、[Liquipedia：Game Settings（Quick Cast）](https://liquipedia.net/dota2/Doubletap)、[Wikipedia：Lockstep protocol](https://en.wikipedia.org/wiki/Lockstep_protocol)（「收到」回應藏延遲是 Age of Empires「1500 Archers」一文在論壇上的轉述，沒讀到原文）。Liquipedia 與 Dota 2 Wiki 擋自動抓取（403／402），Dota 的條目只用搜尋摘要能直接佐證的部分，細節（前搖取消要不要扣冷卻）沒讀到原文，不寫。

## 4. 「各種模式都是回合切片和連接」：分兩層回答

**切片層已經具備**：
- 模擬一律 1/60 秒固定步長（ADR 0016）。
- 指令在 tick 開頭套用並記錄（ADR 0015），所以可回放、可 undo。
- 誰下指令（`controller`：AI／PLAYER）和模擬分開（ADR 0022）。
- 時間怎麼走由 `effectiveTimeScale` 推導（ADR 0025 的瞄準放慢、暫停）。
- 證據：主角閒著時 1～3 tick 就反應（§2 A，10 筆）。

各模式在這一層的差別只是「誰下指令」和「時鐘怎麼走」：

| 模式 | 誰下指令 | 時鐘 |
| :-- | :-- | :-- |
| 掛機／展示 | 全部 AI | 一直走 |
| 即時（PLAY 現在） | 主角玩家，其他 AI | 一直走，瞄準時放慢 |
| 即時可暫停（RTwP） | 同上 | 玩家隨時暫停下令（已有暫停鈕） |
| 半回合（ATB 的等待模式） | 同上 | 有單位輪到行動、在等玩家下令時停住 |
| 回合 | 同上 | 只有本回合所有指令都下完才推進一段 |

**回合、半回合還缺兩樣，它們不是切片**：
1. **時鐘閘門**：「什麼條件下時鐘停住、等誰下令」。現在只有暫停鈕與瞄準放慢；要做半回合，需要一個由規則推導的閘門（例：主角前搖結束、沒有指令時停住），和瞄準放慢一樣由狀態推導，不新增倍率的寫入者。
2. **行動資源規則**：回合制的「一回合能做多少事」（行動點、移動格數）。現在單位的節奏由冷卻、前搖、移動速度決定，沒有回合的單位。這會改變平衡的意義，是遊戲設計題，不是工程題。

**這次的延遲正是「連接」那一段的問題**：指令進模擬之後，由誰、按什麼優先順序打斷正在做的事。AI 的防抖規則適合沒人看著的模擬，套到玩家身上就變成延遲。回合制也需要同一套「指令能打斷什麼」的規則，所以先把它定清楚，對之後每種模式都有用。

## 5. 修法方向（只列方向，未動工）

**約束**：
- 只對玩家指令生效：場上沒有玩家單位時 `balance:fingerprint` 180／180 必須完全相同（ADR 0022 的後果）。
- 指令仍在 tick 開頭套用（ADR 0015）。
- 「玩家指令能打斷什麼」寫在一處（一張規則表），不在 `OrderMove`／`OrderCast`／`MovementSystem` 各判一次（不做耦合）。

| 包 | 內容 | 解決 |
| :-- | :-- | :-- |
| C1 | 玩家指令可取消自己的前搖：前搖還沒走完就換指令＝取消，不扣魔、不進冷卻（`commitSkill` 才扣，現況就是這樣）。奧義前搖 1.5～2 秒要不要也能取消，看 Q2 | §2 A 普攻前搖 0.48 秒 |
| C2 | 玩家的新移動指令立刻換路，不套 `REPATH_MIN_S` | §2 A 走路改向 0.25 秒 |
| C3 | 施放指令放不出來時的規則，看 Q1 | §2 B 乾站 |
| C4 | 自身技（射程 0）的玩家指令不經 AI 的「值不值得放」，按了就放 | §2 B 自身技等不到 |
| C5 | 輸入：PLAY 模式下令改在按下時送；拖鏡頭和下令分開，看 Q3 | §2 C 漂移掉指令 |
| C6 | （選配）Quick Cast：按技能鍵直接對游標下的目標放 | 少一次點擊 |

驗收（先寫紅）：C1、C2、C4 各一則 `tests/PlayerOrders` 情境（固定種子，量 tick 數）；指紋 180／180 不變；`E2E_ONLY=play` 全過；本機實跑（`render-verify`）。C1 碰前搖狀態機（`SkillStateMachine` 的 `INTERRUPT` 邊，普攻已有「打斷回到就緒」），要先讀 ADR 0012。

## 6. 要使用者決定

- **Q1 冷卻中、魔力不足按技能**：(a) 不收指令，按鈕變暗並提示（MOBA 做法，推薦）；(b) 收下排隊，等待期間照姿態普攻（不會乾站，但等多久不可預期）。
- **Q2 奧義前搖（1.5～2 秒）能不能被玩家取消**：能取消比較貼手，但會讓「詠唱預警」被當成假動作。
- **Q3 拖鏡頭的方式**：PLAY 的鏡頭本來會跟著主角。(a) 左鍵只下令，拖鏡頭改右鍵或中鍵（推薦）；(b) 維持左鍵拖，但門檻加大。觸控另外看。
- **Q4 這幾包誰做**：C1 碰前搖狀態機、C2 碰移動系統，都是跨系統規則，主代理自己做比外派穩；C5、C6 是輸入層，可拆。
