# 打光與特效的成本：量測、已做的、接下來（2026-11-28）

> 主席 Fable 5.2。使用者 11-28：打光「不論如何都不可以被關掉」（已做，ADR 0030、WORKLOG §2 DR）；「過往特效管線那些仿光效硬畫的是不是應該全面改光效通道減少材質體積？面數本身就會影響打光反射取樣不是嗎？還是我觀念有錯？總之你處理效能部分到你滿意，視覺也是。我只有一個需求，現代化！」
> 方向由主席決定；合併與 push 照舊要問。C0、C1 已做（§4），其餘是接下來的順序（§5）。

## 1. 目標

打光常開之後，把它在桌機與手機上的成本降下來，並把渲染管線往「精靈由顯示卡畫、光是真的光」推進。不得用「關掉打光」當手段（ADR 0030）。
量化目標：桌機 RTX 4070、2560×1440 全景，打光的額外成本從量測起點的每幀 5.2 ms 降到 2 ms 以下；手機 iPhone 實機打光開著能留在品質階層 1 以內（實機還沒量）。

## 2. 量測

工具：`npm run perf:lit-cost`（`tools/ui-e2e/lit-cost.mjs`，C0）。固定的凍結戰鬥（保真工具的種子時鐘、種子陣容、固定地圖），每種做法開一個新頁面、畫完全相同的幀；逐幀同步推進（沒有 vsync），每段結束強制顯示卡做完再計時；有視窗、強制 RTX 4070、2560×1440、DPR 1、品質階層釘 0、開發伺服器。場景（第 3 段結束時）：地塊 169、玩法標示 42、障礙物 18、單位 9、特效 101、光環 3、危害 7、粒子 141。
輸出 `tools/ui-e2e/out/lit-cost.json`；顯示卡字串 `ANGLE (NVIDIA, NVIDIA GeForce RTX 4070 (0x00002786) Direct3D11 vs_5_0 ps_5_0, D3D11)`。

| 做法 | 每幀 ms | 和完整打光的差 |
| :-- | --: | --: |
| 完整打光 | 9.94 | — |

| 只把世界改畫到離屏畫布 | 4.59 | −5.36 |
| **不做遮罩（`tag` 整個跳過）** | 5.59 | **−4.35** |
| 遮罩不處理單位（9 個） | 8.08 | −1.86 |
| 遮罩不處理障礙物（18 個） | 7.95 | −1.99 |
| 遮罩不處理地塊（169 個） | 8.20 | −1.74 |
| 遮罩不重畫特效類 op | 8.63 | −1.31 |
| 做遮罩、不上傳也不跑 GL | 8.23 | −1.71 |
| 不上傳畫布（GL 用舊貼圖） | 8.02 | −1.93 |
| 點光數量歸零（9 盞） | 9.10 | −0.84 |
| 完整打光，特效類 op 完全不畫 | 7.71 | −2.23 |
| 不打光，特效類 op 完全不畫 | 4.11 | （比不打光少 0.65） |

同一做法重跑的差約 ±0.1 ms（完整打光 9.94、10.03）；但機器有別的負載時整組會一起慢三成（一次量到不打光 6.4 ms），所以**每次都要連不打光的對照組一起量，看差與比例，不跨次比絕對值**。

### 2.2 讀得出來的

1. 打光讓每幀從 4.75 變成 9.94 ms。線上版實測也是這個比例（WORKLOG §2 DR：打光開 45～192 FPS、關 56～229）。
2. **八成以上是遮罩（4.35 ms），不是著色器**。遮罩是用 Canvas 2D 把東西再畫一次：單位、障礙物、地塊、特效四塊都在 1.3～2 ms。
3. GL 那一段主要是畫布上傳（1.9 ms）與點光：9 盞點光 0.84 ms，約 0.09 ms 一盞（每盞是一個帶地面投影取樣的矩形）。展示模式 16～20 個單位照比例是 1.5～1.9 ms，**這是推算**。全螢幕的著色、泛光、合成扣掉這兩項之後量不出來。
4. 特效類 op 全部加起來，不打光是 0.65 ms，打光是 2.23 ms（多畫一次遮罩、再加上傳）。

### 2.3 限制

開發伺服器；只有這一台機器；場上 9 個單位（展示模式常有 16～20 個）；手機沒量。

## 3. 第一性原則：成本到底花在哪

回答使用者的問題，也是之後每一包的判斷依據。

- **這個渲染器執行期沒有多邊形。** 單位、障礙物、地塊、特效零件都是事先烘好的 2D 圖，畫面是把這些圖一張一張貼上去。所以「面數」不影響打光。打光有兩種成本：全螢幕那一趟對每個像素算一次，跟**解析度**成正比、跟場上有多少東西無關，量不出來；**每一盞點光**另外算一次它照得到的範圍（含投影取樣），量到約 0.09 ms 一盞，跟光的數量成正比。
- **真正貴的是「貼圖的次數」**。Canvas 2D 每貼一張圖要幾微秒到幾十微秒，而且是一張一張送；一幀幾百到上千次。不打光的 4.75 ms 幾乎都是這個，打光多出來的 5.2 ms 也是這個（為了告訴著色器「這個像素是單位、是特效還是地面」，把東西用 Canvas 2D 再貼一次）。
- **仿光效特效（`glow` 零件，`data/vfx` 裡 100 處，用得最多）該不該改成光：方向對，但理由不是它最貴，而且「改成哪一種光」要先量。** 它是貼圖次數的一部分，不是大宗（上面第 4 點）。一盞帶投影的點光約 0.09 ms，一張光暈貼圖打光時貼兩次約 0.01～0.02 ms：把每個光暈都換成現在這種點光會更貴。便宜的做法有兩條，C2 先量再選：不帶投影的光（省掉取樣），或沿用已經有的特效餘光（`LIGHTING.GLOW_LIGHT`：把畫面上亮的地方抹開當成光，不管幾個特效成本都一樣）。值得改的三個理由：
  1. 打光之下每個特效要貼兩次，少一個零件省兩次。
  2. 記憶體：特效零件快取是手機上最大的畫布類別（`perf:mem` 量到 143～250 MB），光暈是大張的漸層圖；改成光之後這些圖不用烘、不用存。
  3. 畫面：光暈只是蓋在圖上的一層顏色，照不到地面和旁邊的單位；真的光會。這才是「現代化」看得到的部分。
- **現代化的終點是精靈改由顯示卡成批畫**：全部單位、地塊、零件一次送出，同時輸出顏色和「這是什麼」的資訊。這樣遮罩不用再畫第二次（4 ms 歸零），基礎的 4.75 ms 也會大幅下降。它是一輪架構改動（要動 ADR 0029 的「世界仍由 Canvas 2D 畫」、座標協議、保真基準），C5 另外開案；在那之前先把現有架構裡便宜的做掉。

## 4. 已做

### C0 量測工具（`npm run perf:lit-cost`）

見 §2。做法靠成員名稱修補執行中的 `LightingPass`／`RenderDispatcher`；成員改名會直接失敗，不會默默量到沒修補的路徑。

### C1 直立物遮罩（單位、障礙物）

每一步都先量再改，失敗的也記在這裡。

| 步驟 | 結果 | 證據 |
| :-- | :-- | :-- |
| 假設「整張暫存畫布每次被改寫前要先複製」，改用跟直立物一樣大的小暫存畫布 | **變慢**（完整打光 9.94 → 11.37），還原 | 每個直立物從讀 1 次畫布變成讀 3 次；成本跟「畫布被讀幾次」成正比，不是跟畫布大小 |
| 驗證：章照蓋、但不把暫存畫布貼進幾何遮罩 | 省 2.43 ms | 27 個直立物、每個讀一次暫存畫布，每次約 0.09 ms（瀏覽器要先把那張畫布累積的繪製送出去） |
| **暫存畫布分格排版，整幀畫完才一次貼進幾何遮罩** | 完整打光 9.94 → 8.81（不打光 4.75 → 4.79） | `perf:lit` 六張和改前比：每張 92 萬像素差 0～4 個像素 |
| 剪影的透明度改由呼叫端決定（單位的 painter 只畫形狀），打光遮罩畫 1 次取代 4 次 | 8.81 → 8.70，在雜訊內；留著是因為少了三處各自乘透明度的程式 | 遮擋剪影的外觀不變（`perf:fidelity`）；打光畫面只差單位邊緣的半透明像素（0.3～1.3% 的像素） |
| 蓋章從 `source-in` 改成 `source-atop`（結果相同、不用另開一層） | 量的時候機器有別的負載，分不出來；留著 | 同上那次截圖比對 |

補驗（同一個工作階段在 main 與分支各拍一次再比）：
- 遮擋剪影（Canvas 2D 路徑，`tools/ui-e2e/out/occlusion-probe.mjs`，不進版控）：保真工具的凍結幀有 4 個被擋住的單位，main 與分支 0 差異。
- `npm run perf:lit -- --walk 60`：靜止六張差 0.27～1.3% 的像素、走路連續格差 2.4%，都在單位輪廓邊緣（一次畫 68% 和 25% 畫四次在半透明邊緣的覆蓋率不同）；放大對照看不出差別。
- 格子排滿時幀中途先貼一次（`beginItem` 裡的 `flushItems`）：暫時強制每個直立物都中途貼，六張和正常版差 0～18 個像素。這條路在手機上是常態：直向 393×852、DPR 3、鏡頭縮放 1 時遮罩 590×1278，一個單位的格子約 126×297，大約 16 個直立物就排滿。
- 行為有一處改變：剪影（遮擋剪影與打光遮罩）現在會跟著出場淡入、墜落淡出一起變淡；以前固定 25%。

C1 之後的完整數字見 §4.1。

渲染線同時只開一條，依序做；每包用 `npm run perf:lit-cost`（連對照組）與 `npm run perf:lit` 截圖驗收。

| 包 | 內容 | 為什麼排這裡 | 執行者 |
| :-- | :-- | :-- | :-- |
| C2 | 仿光效零件改成光。第一步只量：在 `perf:lit-cost` 加「N 盞光」的做法（帶投影、不帶投影各一），和同樣數量的光暈貼圖比；再決定 `glow` 零件在打光開啟時改成哪一種（不帶投影的點光，或只靠特效餘光）。「哪些零件是仿光效」只定義在零件表一處，讀打光狀態的地方只有一處 | 使用者要的方向；做對了同時少畫、省快取記憶體、光會照到場景；做錯了（每個光暈一盞帶投影的光）會比現在貴 | 量測與定調（幾招代表技能，看連續畫面）由主席；之後逐招套用可拆給 agy Neon |

## 7. 已知風險

- 量測只在這台機器、開發伺服器；手機的瓶頸可能不同（METHODOLOGY §4 第 9 條），C6 之前不能假設桌機的排名適用。
- C2：點光每盞約 0.09 ms、上限 64 盞；光暈零件一對一換成點光在特效多的時候會比現在貴，也會超過上限。量完才定做法與取捨規則。
- 單位的點光本身就是成本：20 個單位約 1.5～1.9 ms（推算）。C3 之後若它變成最大項，要看投影取樣能不能依距離或階層減少。
- C3：玩法標示改由著色器擋之後，被前方高地塊擋住的單位身上會少一塊標示的顏色（現在幾何遮罩在那裡本來就不準）。

**已經量到的（不要重新發現）**
- 成本跟「一張畫布被讀幾次」成正比：畫布當成 `drawImage` 的來源或上傳成貼圖時，瀏覽器要先把它累積的繪製送出去，每次約 0.09 ms（27 個直立物各讀一次＝2.4 ms）。改用小暫存畫布反而更慢（讀的次數變多）。
- 單位的整套繪製（`drawAssembly`）很便宜：12 次降到 3 次只省 0.1 ms。
- 每個直立物現在還有：兩個裁切、一次蓋章、兩次 `destination-out` 挖洞（特效遮罩與玩法標示遮罩）。`item_no_stamp` −1.3、`item_no_cut` −1.2、`item_no_cell` −1.5 ms（27 個；各項不能相加）。
- 可以考慮但沒驗證的方向：`tag` 改成畫完世界之後依遮罩分三趟重畫（同一張遮罩的繪製連在一起，三張遮罩可以排在同一張畫布上只上傳一次）；玩法標示遮罩不由直立物挖洞，改在著色器用幾何遮罩擋；背景不經 GL（GL 輸出透明底疊在背景上，要保留背景的調色）；障礙物是靜態精靈，蓋好章的圖可以快取。
- 點光約 0.09 ms 一盞（9 盞 0.84 ms）。

**驗收怎麼跑**
- 數字：`npm run perf:lit-cost`，每次都含 `full` 與 `direct`；只比同一次裡的差。機器有別的負載時整組會一起慢三成，看到 `direct` 不在 4.6～4.9 就重跑。同一份程式重跑兩次的差當雜訊，改動的效果要超過它才算。
- 畫面：同一個工作階段在 main 與分支各跑 `npm run perf:lit -- --walk 60`，逐像素比（`tools/ui-e2e/out/` 裡有 `lit-main-walk/` 當 main 的對照，用 PIL 的 `ImageChops.difference`）。這一批相對 main 的差應該接近 0；超過「靜止 1.3%、連續格 2.4%」或出現單位邊緣以外的差異就停下來看圖。
- 幀中途貼圖的路徑（`beginItem` 裡的 `flushItems`）改過的話，暫時強制每個直立物都中途貼一次，和正常版比（應差 20 個像素以內），驗完還原。
- `npm run perf:guard`：保真六張的數字要和 main 相同（VOID 0.296、FOREST 0.659、ICE 0.302、MAGMA 0.614、DESERT 0.500、battle_frozen 0.177）。
- 每個 commit 前：`npm run lint && npm test && npm run build`、`npm run knip`、`node tools/ui-e2e/runtime-smoke.mjs`。進入點目前 257,371／257,500 位元組，動 `RenderPipeline.ts` 會吃這個預算，超過就先在別處騰空間，不改預算。
- `e2e:ui`、`e2e:play` 在 main 上本來就有 PLAY 瞄準類的偶發紅（三次兩次），回報紅的次數與項目即可，不為它改程式。

**環境**
- 這台機器副螢幕接 AMD 內顯（56 Hz）：有視窗的量測工具已經加 `--force_high_performance_gpu`；自己寫探針時要讀 `UNMASKED_RENDERER_WEBGL` 寫進輸出。
- 用 vite 的閘門（smoke、perf、e2e）在跑的時候不要改原始碼（HMR 會讓那次結果不可信）。
- 臨時探針寫在 `tools/ui-e2e/out/`（不進版控），含反斜線的檔案內容用 Write 工具寫。
- 重量測（`perf:lit-cost`、`perf:guard`、`e2e`）一次只跑一個。

**固定三條**：只結束自己啟動的行程（記下 PID，不用名稱或萬用條件）；不為了過檢查改造形或改驗收（保真基準不重錄、門檻與預算不放寬）；不新增耦合（同一個判斷不在多處重複，數值進 `constants/lighting.ts`）。

**什麼時候停下來回報（不要硬做）**
- 額外成本到 2 ms 以下，或 P2、P3 能試的都試過了。
- 畫面出現上面允許範圍以外的差異、修不掉。
- 要動 `RenderSpec` 的座標協議、要推翻 ADR、或進入點預算騰不出空間。
- 同一個問題試兩次不過：先查是不是規則或架構造成的，是就回報。
