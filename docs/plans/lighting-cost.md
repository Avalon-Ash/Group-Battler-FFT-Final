# 打光與特效的成本：初步量測與拆包提案（2026-11-28）

> 主席 Fable 5.2。使用者 11-28 實機回饋：打光「不論如何都不可以被關掉」（已做，ADR 0030、WORKLOG §2 DR）；「接下來就是優化工作，有光效很多特效可以砍掉用光效替換，因為現在最大成本都是舊時代的仿光效特效」。
> 本檔只有量測與提案，還沒有改效能相關的程式。**量測結果和「最大成本是仿光效特效」不一致（§2），先做哪一包要使用者決定（§5）。**

## 1. 目標

打光常開之後，把它在桌機與手機上的成本降下來：桌機 RTX 4070、2560×1440 的展示模式不再因為打光掉到 100 FPS 以下；手機（iPhone 實機）打光開著能維持在品質階層 1 以內。不得用「關掉打光」當手段（ADR 0030）。

## 2. 初步量測

### 2.1 線上版，使用者看到的情況

`node tools/ui-e2e/out/lit-timeline-probe.mjs "https://avalon-ash.github.io/Group-Battler-FFT-Final/" 75`（探針不進版控；一般 Chrome 視窗、不加 GPU 旗標、2544×1345、展示模式，每 3 秒一筆）。顯示卡 `ANGLE (NVIDIA, NVIDIA GeForce RTX 4070 (0x00002786) Direct3D11 vs_5_0 ps_5_0, D3D11)`。

- 打光開著（0～45 秒，16 筆）：45～192 FPS，多數在 65～150。
- 第 48 秒被自動關掉（當時的版本）之後（9 筆）：56～229 FPS，多數在 130～229。

### 2.2 逐項關閉（開發伺服器，同一頁原地切換）

`node tools/ui-e2e/out/lit-cost-ab.mjs --calm --seconds=2.5 --rounds=4`（探針不進版控；有視窗、強制 RTX 4070、關 vsync 與幀率上限、2560×1440、DPR 1、品質階層釘 0；每種做法輪流量、每輪反向，取第 3、4 輪平均）。
場景：全景鏡頭，地塊 127、障礙物 12、玩法標示 36、危害 16、特效 49、粒子 49、單位 3。**戰鬥在第 1 輪後就結束了**（鎖血沒擋住），第 2～4 輪是靜止的結算畫面，三輪的 op 數完全相同；第 1 輪的數字不採用。

| 做法 | 每幀 ms | 和完整打光的差 |
| :-- | --: | --: |
| 完整打光 | 4.71 | — |
| 不打光（原本的直接路徑） | 1.85 | −2.86 |
| 只把世界改畫到離屏畫布（不做遮罩、不跑 GL） | 1.80 | −2.91 |
| 做遮罩、不跑 GL 也不上傳 | 4.53 | −0.18 |
| **不做遮罩（`tag` 整個跳過）** | 2.71 | **−2.00** |
| 遮罩不重畫特效類 op | 4.31 | −0.40 |
| 遮罩不處理單位（3 個） | 4.13 | −0.58 |
| 點光數量歸零 | 4.77 | +0.06 |
| 不上傳畫布（GL 用舊貼圖） | 4.60 | −0.11 |
| 投影取樣 16 → 4 次 | 4.71 | 0.00 |
| 完整打光，特效類 op 完全不畫 | 3.82 | −0.89 |
| 不打光，特效類 op 完全不畫 | 1.30 | （比不打光少 0.55） |

同一工具另外兩次的場景更不穩（鏡頭拉近只看到 3 個單位；20 人回放量到一半只剩 1 人），只當旁證：鏡頭拉近、特效 172 個時，打光多 1.0 ms、不上傳省 0.7 ms、不打光時特效類 op 合計 0.25 ms。

### 2.3 讀得出來的

1. **打光在全景下讓每幀從 1.85 ms 變成 4.71 ms**，比畫面上其他東西加起來還多。
2. **最大的一塊是遮罩重畫（`LightingPass.tag`，約 2.0 ms）**，都是 Canvas 2D 的繪製：每個單位的剪影畫三張畫布、每張 `SILHOUETTE_REPEAT` 次；每個障礙物分發三次；特效、投射物、危害、玩法標示各多畫一次；每個地塊多兩個呼叫。
3. **GL 那一段（著色、泛光、合成）很小**：這個場景約 0.2 ms；投影取樣次數、點光數量在這裡量不出差別。畫布上傳在兩個場景差很多（0.1 與 0.7 ms），還不能下結論。
4. **特效類 op 全部加起來，不打光時是 0.25～0.55 ms；打光時因為多畫一次遮罩變成 0.5～0.9 ms**。把特效全部拿掉，完整打光的幀時間也只少一成到兩成：仿光效特效不是最大成本。
5. `data/vfx` 裡 `glow` 零件有 100 處，是用得最多的零件種類；用光取代它在資料面做得到，但能省的上限就是第 4 點那個數字裡的一部分。

### 2.4 這份量測的限制

- 場上只有 3 個存活單位。單位遮罩 3 個就占 0.58 ms，展示模式常有 16～20 個；照比例推是 3～4 ms，**這是推算，沒有量**。
- 開發伺服器（沒壓縮、沒最佳化），不是正式版；只有這一台機器；關 vsync 的 rAF 間隔同時含 CPU 與 GPU，分不開。
- 各項相加（2.0＋0.18）不等於總差（2.86）：有些成本只在兩件事同時做時才出現。
- 手機完全沒量。

## 3. 架構上要守的

- 「這個零件是仿光效」只定義在零件表一處；讀打光狀態的地方只有一處，不在各個 painter 裡散落判斷。
- Canvas 2D 路徑還在（`?lit=0`、WebGL2 拿不到、context 遺失期間），保真基準只對應它。它要保留舊光暈（基準不動，只有打光時省），還是一起拿掉（照 `rebaseline-fidelity` 取證重錄），在動 C3 之前要使用者決定。
- 動到 `tag` 的繪製點要對照 `engine/renderers/RenderSpec.ts` §1 尾段，同一個 commit 更新它與檔頭。
- 渲染線同時只開一條：下面各包依序做，不並行。

## 4. 拆包（提案）

| 包 | 內容 | 預期 | 建議執行者 | 驗收 |
| :-- | :-- | :-- | :-- | :-- |
| C0 | 量測工具進版控（`perf:lit-cost`）：凍結戰鬥的固定 20 人場景（`tools/ui-e2e/lib/frozen-battle.mjs`）、正式版 build、逐項關閉、同設定三段量雜訊、顯示卡字串寫進輸出 | 把 §2.4 的洞補上；之後每包用它驗收 | 主席（探針前提要自己驗，METHODOLOGY §4 第 11 條） | 同設定三段的差小於要比的差；op 數在量測期間不變 |
| C1 | 遮罩重畫降成本：單位剪影每幀只畫一次到暫存、其餘重用；障礙物是靜態的，鏡頭與地圖沒變時整層沿用；地塊只在有疊層或鋪設時才呼叫 | 最大項；全景約 −1～2 ms（推算） | 主席（前後相依、要看連續畫面） | C0 的數字；`perf:lit` 截圖與 `--walk 60` 和改前逐像素相同或只差預期處 |
| C2 | 特效類 op 不畫兩次（做法要先試：遮罩改記類別而不是重畫、或特效只畫進自發光層由著色器合成） | 打光時特效成本減半 | 主席先做原型，定案後可拆 | 同上，加 `perf:vfx-strip` 帶 `lit=1` |
| C3 | 用光取代仿光效零件：`glow` 零件在打光開啟時不畫，改登記成點光（上限 `LIGHTING.MAX_LIGHTS`） | 上限是特效成本的一部分（§2.3 第 4、5 點）；畫面上光會照到地面與單位 | 定調由主席；資料表逐招套用可拆給 agy Neon | C0 的數字；盲評不低於現在；Canvas 2D 路徑保真不變（或照決定重錄） |
| C4 | 上傳：背景沒變時不重傳、遮罩解析度依品質階層再縮 | C0 量完才知道值不值得 | 主席 | C0 的數字 |
| C5 | 手機：依品質階層降打光成本（投影取樣、泛光次數、遮罩倍率） | 等 iPhone 實機數字 | 主席 | 實機 `?perf` A/B（METHODOLOGY §4 第 9、17 條） |

## 5. 停下來問使用者

1. **先做哪一包**：量測指向 C0 → C1 → C2（打光自己的成本）；使用者原本的方向是 C3。兩者不衝突，C3 的收益上限比較低，而且 C2 做完之後才知道 C3 還剩多少可省。
2. C3 動工前：Canvas 2D 路徑要不要保留舊光暈（§3 第二條）。
3. C1 之後若全景仍低於目標，再決定遮罩解析度要不要降（畫面邊緣會變軟）。

## 6. 已知風險

- §2 的數字來自不穩定的場景；C0 做完若結論不同，本檔的順序要改。
- 單位剪影重用時，移動中的單位遮罩要跟著位移，否則光池與影子會落後一幀（要看 `--walk` 連續畫面）。
- 特效改成只畫進自發光層的話，特效和單位、障礙物的前後遮擋要另外處理（現在靠世界畫布的繪製順序）。
