## 1. 目標

打光常開之後，把它在桌機與手機上的成本降下來，並把渲染管線往「精靈由顯示卡畫、光是真的光」推進。不得用「關掉打光」當手段（ADR 0030）。
量化目標：桌機 RTX 4070、2560×1440 全景，打光的額外成本從量測起點的每幀 5.2 ms 降到 2 ms 以下；手機 iPhone 實機打光開著能留在品質階層 1 以內（實機還沒量）。

## 2. 量測

工具：`npm run perf:lit-cost`（`tools/ui-e2e/lit-cost.mjs`，C0）。固定的凍結戰鬥（保真工具的種子時鐘、種子陣容、固定地圖），每種做法開一個新頁面、畫完全相同的幀；逐幀同步推進（沒有 vsync），每段結束強制顯示卡做完再計時；有視窗、強制 RTX 4070、2560×1440、DPR 1、品質階層釘 0、開發伺服器。場景（第 3 段結束時）：地塊 169、玩法標示 42、障礙物 18、單位 9、特效 101、光環 3、危害 7、粒子 141。
輸出 `tools/ui-e2e/out/lit-cost.json`；顯示卡字串 `ANGLE (NVIDIA, NVIDIA GeForce RTX 4070 (0x00002786) Direct3D11 vs_5_0 ps_5_0, D3D11)`。

同一做法重跑的差約 ±0.1 ms（完整打光 9.94、10.03）；但機器有別的負載時整組會一起慢三成（一次量到不打光 6.4 ms），所以**每次都要連不打光的對照組一起量，看差與比例，不跨次比絕對值**。

### 2.2 讀得出來的

1. 打光讓每幀從 4.75 變成 9.94 ms。線上版實測也是這個比例（WORKLOG §2 DR：打光開 45～192 FPS、關 56～229）。
2. **八成以上是遮罩（4.35 ms），不是著色器**。遮罩是用 Canvas 2D 把東西再畫一次：單位、障礙物、地塊、特效四塊都在 1.3～2 ms。
3. GL 那一段主要是畫布上傳（1.9 ms）與點光：9 盞點光 0.84 ms，約 0.09 ms 一盞（每盞是一個帶地面投影取樣的矩形）。展示模式 16～20 個單位照比例是 1.5～1.9 ms，**這是推算**。全螢幕的著色、泛光、合成扣掉這兩項之後量不出來。
4. 特效類 op 全部加起來，不打光是 0.65 ms，打光是 2.23 ms（多畫一次遮罩、再加上傳）。

### 2.3 限制

開發伺服器；只有這一台機器；場上 9 個單位（展示模式常有 16～20 個）；手機沒量。

## 3. 第一性原則：成本到底花在哪

回答使用者的問題，也是之後每一包的判斷依據。

- **這個渲染器執行期沒有多邊形。** 單位、障礙物、地塊、特效零件都是事先烘好的 2D 圖，畫面是把這些圖一張一張貼上去。所以「面數」不影響打光。打光有兩種成本：全螢幕那一趟對每個像素算一次，跟**解析度**成正比、跟場上有多少東西無關，量不出來；**每一盞點光**另外算一次它照得到的範圍（含投影取樣），量到約 0.09 ms 一盞，跟光的數量成正比。
- **真正貴的是「貼圖的次數」**。Canvas 2D 每貼一張圖要幾微秒到幾十微秒，而且是一張一張送；一幀幾百到上千次。不打光的 4.75 ms 幾乎都是這個，打光多出來的 5.2 ms 也是這個（為了告訴著色器「這個像素是單位、是特效還是地面」，把東西用 Canvas 2D 再貼一次）。
- **仿光效特效（`glow` 零件，`data/vfx` 裡 100 處，用得最多）該不該改成光：方向對，但理由不是它最貴，而且「改成哪一種光」要先量。** 它是貼圖次數的一部分，不是大宗（上面第 4 點）。一盞帶投影的點光約 0.09 ms，一張光暈貼圖打光時貼兩次約 0.01～0.02 ms：把每個光暈都換成現在這種點光會更貴。（P4 更正：點光的 0.09 ms 是量測偏差，桌機上點光比光暈貼圖便宜，§5.1。）便宜的做法有兩條，C2 先量再選：不帶投影的光（省掉取樣），或沿用已經有的特效餘光（`LIGHTING.GLOW_LIGHT`：把畫面上亮的地方抹開當成光，不管幾個特效成本都一樣）。值得改的三個理由：
  1. 打光之下每個特效要貼兩次，少一個零件省兩次。
  2. 記憶體：特效零件快取是手機上最大的畫布類別（`perf:mem` 量到 143～250 MB），光暈是大張的漸層圖；改成光之後這些圖不用烘、不用存。
  3. 畫面：光暈只是蓋在圖上的一層顏色，照不到地面和旁邊的單位；真的光會。這才是「現代化」看得到的部分。
- **現代化的終點是精靈改由顯示卡成批畫**：全部單位、地塊、零件一次送出，同時輸出顏色和「這是什麼」的資訊。這樣遮罩不用再畫第二次（4 ms 歸零），基礎的 4.75 ms 也會大幅下降。它是一輪架構改動（要動 ADR 0029 的「世界仍由 Canvas 2D 畫」、座標協議、保真基準），C5 另外開案；在那之前先把現有架構裡便宜的做掉。

## 4. 已做

### C0 量測工具（`npm run perf:lit-cost`）

見 §2。做法靠成員名稱修補執行中的 `LightingPass`／`RenderDispatcher`；成員改名會直接失敗，不會默默量到沒修補的路徑。

### C1 直立物遮罩（單位、障礙物）

每一步都先量再改，失敗的也記在這裡。

| 步驟 | 結果 | 證據 |
| :-- | :-- | :-- |
| 假設「整張暫存畫布每次被改寫前要先複製」，改用跟直立物一樣大的小暫存畫布 | **變慢**（完整打光 9.94 → 11.37），還原 | 每個直立物從讀 1 次畫布變成讀 3 次；成本跟「畫布被讀幾次」成正比，不是跟畫布大小 |
| 驗證：章照蓋、但不把暫存畫布貼進幾何遮罩 | 省 2.43 ms | 27 個直立物、每個讀一次暫存畫布，每次約 0.09 ms（瀏覽器要先把那張畫布累積的繪製送出去） |
| **暫存畫布分格排版，整幀畫完才一次貼進幾何遮罩** | 完整打光 9.94 → 8.81（不打光 4.75 → 4.79） | `perf:lit` 六張和改前比：每張 92 萬像素差 0～4 個像素 |
| 剪影的透明度改由呼叫端決定（單位的 painter 只畫形狀），打光遮罩畫 1 次取代 4 次 | 8.81 → 8.70，在雜訊內；留著是因為少了三處各自乘透明度的程式 | 遮擋剪影的外觀不變（`perf:fidelity`）；打光畫面只差單位邊緣的半透明像素（0.3～1.3% 的像素） |
| 蓋章從 `source-in` 改成 `source-atop`（結果相同、不用另開一層） | 量的時候機器有別的負載，分不出來；留著 | 同上那次截圖比對 |

補驗（同一個工作階段在 main 與分支各拍一次再比）：
- 遮擋剪影（Canvas 2D 路徑，`tools/ui-e2e/out/occlusion-probe.mjs`，不進版控）：保真工具的凍結幀有 4 個被擋住的單位，main 與分支 0 差異。
- `npm run perf:lit -- --walk 60`：靜止六張差 0.27～1.3% 的像素、走路連續格差 2.4%，都在單位輪廓邊緣（一次畫 68% 和 25% 畫四次在半透明邊緣的覆蓋率不同）；放大對照看不出差別。
- 格子排滿時幀中途先貼一次（`beginItem` 裡的 `flushItems`）：暫時強制每個直立物都中途貼，六張和正常版差 0～18 個像素。這條路在手機上是常態：直向 393×852、DPR 3、鏡頭縮放 1 時遮罩 590×1278，一個單位的格子約 126×297，大約 16 個直立物就排滿。
- 行為有一處改變：剪影（遮擋剪影與打光遮罩）現在會跟著出場淡入、墜落淡出一起變淡；以前固定 25%。

### 4.2 P1：工具修正與細項（第二批，分支 `perf/lighting-cost-2`）

量測工具先修了三處（`tools/ui-e2e/lit-cost.mjs`）：
- **第一頁偏差**：同一份程式在同一次執行裡，第一個頁面 `full` 7.66／8.01／12.87 ms、之後的頁面 `full_again` 7.31／7.01／11.86 ms（三段）。現在正式量測前先跑一個不計時的頁面；`full_again`、`direct_again` 在後面的頁面再量一次對照組，同一次執行就看得到頁面之間的雜訊。
- `--repeat N`：每個做法輪流開 N 個頁面、合併計算；`noise` 改成「同一段在不同頁面之間的最大差」（以前是三段之間的差，那是場景內容不同，不是雜訊：第 3 段 tick 400～519 在所有做法都重三到四成）。
- 表尾印出「打光的額外成本（full − direct）」。

**這台機器今天比 C1 那次慢**：`direct` 每次 5.6～5.9 ms（C1 時 4.63），三段各慢約 15%（C1 4.20／3.83／6.23，今天約 4.9／4.8／7.2）；同時間使用者自己的 Chrome（不是量測開的）佔顯示卡 3D 約 14%。所以下面一律只比同一次執行裡的差。用修正後的工具重量同一份程式（和 main 相同），**打光的額外成本是 3.06～3.29 ms**（6 次執行），不是 3.52；3.52 有一部分是第一頁偏差。

讀得出來的：
1. 打光的額外成本 3.06 ms 裡，遮罩重畫 2.36 ms；其中**貼地鋪設（法陣）逐格重畫進特效遮罩 0.91 ms 最大**（另一次執行 −0.98～−1.06），特效類 op 0.63，單位 0.33，障礙物 0.16；挖洞、基礎疊層、點光都在雜訊內。
2. 上傳的成本是「把那張畫布累積的繪製點陣化」，不是上傳本身：每張遮罩每幀上傳兩次和一次一樣（`mask_upload_twice` −0.005 ms，`--repeat 3`）。背景上傳在雜訊內。
3. **成本跟解析度關係不大**：同一個場景 1280×720（像素少四倍）額外成本 2.41 ms，2560×1440 是 3.06 ms；約 2.2 ms 是跟像素數無關的固定成本（`node tools/ui-e2e/lit-cost.mjs --size 1280x720 --only direct,full_again,no_tag,no_upload`）。
4. Chrome 追蹤（`browser.startTracing`，30～60 幀，`tools/ui-e2e/out/trace*-*.json`，探針不進版控）：瓶頸在 GPU 行程的主執行緒，不在頁面的 JS。打光開著時 GPU 行程每幀多約 5 ms（追蹤本身會拖慢），裡面是 Skia 解碼與送出 2D 繪製（每幀點陣化任務 43.5 → 55.9 個）與 WebGL 指令（每幀約 7 個任務：5 次上傳各約 0.12～0.24 ms、繪製各趟一個約 1.4 ms 的任務）；頁面主執行緒每幀只多約 0.6 ms，其餘時間在等 GPU 行程。拿掉遮罩裡的鋪設，GPU 行程的 Skia 送出時間每幀 2.80 → 1.28 ms、點陣化任務少 5.4 個。遮罩上每多一個 2D 繪製呼叫，GPU 行程就多一份成本；但鋪設每個呼叫比較貴（每幀約 90 次貼圖、58 次 save、7 次 clip，約 1 ms，平均約 11 µs 一次；P4 的光暈貼圖約 5.6 µs 一次），而且平面與懸空平面兩條路各自拿掉都讓 Skia 送出時間從 3.0 降到 1.4～1.5 ms、點陣化任務少約 3 個，兩條都拿掉是 1.28，不能相加（`tools/ui-e2e/out/trace3-*.json`）。**鋪設為什麼特別貴，成因沒有查明**，是下一步最值得查的一項。

| 上傳不翻轉（`UNPACK_FLIP_Y_WEBGL` 關掉，量時間用） | 沒有效果 | −0.05 ms（`--repeat 3`） |
| 背景不經 GL（§5 C4） | 沒做 | 背景上傳 +0.02 ms，沒有可省的 |
| 玩法標示遮罩不由直立物挖洞、改在著色器擋（§5 C3 後半） | 沒做 | 挖洞只占 −0.06 ms，改了還會動到畫面 |
| 鋪設改由 WebGL 一次 instanced 畫進特效遮罩（同樣的片段與圖層） | 沒做：先量了代價 | 每幀把用到的鋪設圖層上傳成貼圖就要 0.68 ms（`drape_upload_only` −0.34 對 `terrain_no_drape` −1.02），淨省約 0.3 ms、在雜訊內 |
| 懸空平面（詠唱環）的逐格片段在遮罩裡一次畫完 | 沒做 | 逐格是為了排除被擋住的格與施法者那格的前半；一次畫會在地圖邊緣與直立物前後順序上和現在不同，超出允許的差異 |

**P2、P3 的結論**：在 ADR 0029 的架構（世界由 Canvas 2D 畫、遮罩用 Canvas 2D 再畫一次）裡，剩下的成本是遮罩上的重畫；這一批想到的精確等價做法都量過，沒有一個超過雜訊。鋪設那 1 ms 比它的呼叫數該有的貴，成因沒查明（上面第 4 點），查明之後可能還有不用動架構的解法。2 ms 以下要等 §5 C5（精靈由顯示卡成批畫，遮罩跟著同一次繪製輸出，鋪設的 1 ms 與特效的 0.6 ms 才會消失），或接受畫面差異（例如鋪設在遮罩裡不跟著逐格高度）。

### 5.1 P4：光的成本（C2 的第一步，只量、不改特效資料）

做法：在固定場景上多加 N 盞光，位置是 N 個平均分布在地圖上的格子；每盞是一個帶地面投影取樣（16 步）的點光，或把點光著色器的取樣步數設成 0（`lightFrag(0)`，不帶投影，`shaders.ts` 沒改、沒接進正式路徑）。光的範圍 100 世界像素（約一個大型光暈零件），另量一組 64 盞、範圍 300（單位光的範圍）。對照：同樣位置、同樣數量的光暈貼圖，照打光開啟時光暈零件的畫法各畫兩次（世界畫布一次 `lighter`、特效遮罩一次）。用 `--shot` 確認光確實有畫出來：64 盞小範圍光換掉 18 萬個像素、大範圍 147 萬、光暈 176 萬（全畫面 369 萬）。

指令：`node tools/ui-e2e/lit-cost.mjs --repeat 2 --only direct,lights16,lights32,lights64,lights64_wide,lightsns0,lightsns16,lightsns32,lightsns64,glow16,glow32,glow64,full_again`（`tools/ui-e2e/out/p4-final.log`；這次額外成本 3.10 ms，`full_again` 和 `full` 差 +0.05）。

| 多加的東西 | 16 | 32 | 64 | 64（範圍 300） |
| :-- | --: | --: | --: | --: |
| 點光，帶投影 | +0.06 | +0.20 | +0.16 | +0.13 |
| 點光，不帶投影（以「取樣 0 步、不加光」+0.15 為基準） | +0.00 | −0.19 | +0.09 | — |
| 光暈貼圖（世界＋特效遮罩各一次） | +0.31 | +0.81 | +0.72 | — |

單位 ms，和完整打光同一次執行的差；雜訊 0.17～0.54（不帶投影 16 盞那組 1.02、光暈 32 那組 1.12）。

讀得出來的：
1. **在這台桌機上，點光幾乎不花時間**：多 64 盞（帶投影，連範圍 300 的大光）都在 +0.2 ms 以內，在雜訊附近。§2.2 的「0.09 ms 一盞」是第一頁偏差，不成立。為什麼不花時間是推論、沒有直接量：瓶頸在 GPU 行程送出 2D 繪製（§4.2 第 4 點），全部點光是一次 instanced 繪製，著色器的工作可能藏在那段等待裡。
2. **光暈貼圖比點光貴**：64 張 +0.72 ms，每張打光時畫兩次（世界、特效遮罩），每次都是一個 2D 繪製呼叫。
3. 帶不帶投影在桌機上分不出來。手機上會不會分得出來沒有量：著色器的工作量跟「每盞光照到的像素 × 取樣步數」成正比，推論是 GPU 弱的時候才會露出來。另外，範圍 100 的 64 盞只換掉 18 萬像素（光很淡），要像大型光暈那麼顯眼的光比較接近範圍 300 那一列。

**C2 該走哪條路（建議）**：打光開啟時，`glow` 零件不再畫光暈貼圖，改成**不帶投影的點光**（一盞一個 instance，和單位光同一趟）。理由：
- 桌機上比現在便宜（少兩個 2D 繪製呼叫，換一個 instance），而且是「真的光」：照得到地面與旁邊的單位，這是使用者要的「現代化」看得到的部分。
- 不帶投影：**這是為手機做的假設，P4 在桌機上分不出兩者**。特效的光多半貼著地面或在單位身上，投影的視覺差別小；帶投影是每像素 16 次取樣，推論手機上要省的是它。C6 量 iPhone 時一起量兩者，數字出來前先用不帶投影。單位光維持帶投影。
- 只靠特效餘光（`GLOW_LIGHT`）不夠：它延遲一幀、是整片抹開的亮度，沒有位置與衰減，取代不了光暈的形狀。
- 要先處理的：`LIGHTING.MAX_LIGHTS` 64 盞的上限（光暈零件同時出現會超過，§7）；超過時依螢幕面積或亮度取前 N 盞、其餘合併；「哪些零件是仿光效」只在零件表定義一處。手機（C6）要量的是不帶投影的光在 iPhone 上每盞多少，量到之前 C2 的取捨規則先以盞數上限擋。
- 畫面要主席定調（幾招代表技能看連續畫面），使用者實機看過才全面套用（§6 第 3 點）。

**已經量到的（不要重新發現）**
- 成本跟「一張畫布被讀幾次」成正比：畫布當成 `drawImage` 的來源或上傳成貼圖時，瀏覽器要先把它累積的繪製送出去，每次約 0.09 ms（27 個直立物各讀一次＝2.4 ms）。改用小暫存畫布反而更慢（讀的次數變多）。

- 數字：`npm run perf:lit-cost`，每次都含 `full` 與 `direct`；只比同一次裡的差。機器有別的負載時整組會一起慢三成，看到 `direct` 不在 4.6～4.9 就重跑。同一份程式重跑兩次的差當雜訊，改動的效果要超過它才算。
