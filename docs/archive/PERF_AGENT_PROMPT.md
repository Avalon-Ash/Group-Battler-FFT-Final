### 本輪額外規則

- **保真是鐵律**：除 P5 的「降階」（僅在使用者機器慢或被 `?quality` 指定時才生效，預設階層 0 與改前外觀等價）外，**任何會讓 `perf:fidelity` 超標的改動一律還原**，不得放寬門檻或重錄 baseline 來讓測試通過（`--record` 只允許在 P0c 使用一次；若確有「預期外觀變更」必須停下回報）。
- **量測紀律**：所有改前/改後比較在**同一個終端、同一台機器、無其他重負載**下進行；`perf:ab` 一律「交錯兩輪」；單次差距 <5% 視為雜訊，不得據此宣稱有效。優化未達驗收數字 → 還原，不要為了「有改」而保留。
- **不新增依賴**。不使用 `as any`。常數進 `constants.ts`。渲染迴圈內不得 `console.log`。`Agent` 不加方法；不改 `engine/systems/**` 的邏輯（P6 只動 renderers）；不動 facade 簽章。
- 需要 >3 檔才能完成的任務（P4a 已授權 4 檔除外）→ 拆成 `a/b` 兩個 commit 並在報告說明；仍無法 → 停下回報。
- 若 P1a 的 sprite 快取經 3 次嘗試仍無法通過保真或未達 ≥25% 的收益 → **還原 P1 全部變更，保留 P0 護欄，直接前進到 P4**（解析度與品質調度器對慢機器仍有價值），並在報告詳述原因與剩餘手段。
- 時間/額度吃緊時的取捨順序：`P0a→P0b→P0c→P1a/P1b→P4a/P4b→P5a/P5b`（這條線就是對使用者「掉到 60 以下」的直接解），其餘（`P2/P3/P6/P7/P8`）可略並在報告列為未完成。**任何時候中斷都要確保工作樹乾淨且最後一個 commit 全綠。**
- **停工原則**：遇到本文件與 `PERF_FINDINGS.md` 都沒涵蓋、且會改變使用者可見外觀或行為的情況才停下；其餘自行選擇「風險最小、可回退」的做法並記錄在報告。

## 回來後使用者要做的事（給人看）

1. `git log perf/render-opt --oneline`，讀 `docs/PERF_REPORT.md`。
2. **用你自己的電腦量**：`npm run dev`，網址後面加 `?perf`（例如 `http://localhost:5173/?perf`），看畫面上的 FPS 與各階段 ms；再試 `?quality=0`（完整）、`?quality=2`、`?quality=3` 比較。把數字回報給主代理（尤其是：哪個階段最高、DPR 是多少、螢幕解析度）。
3. 目視比對幾個場景（VOID/FOREST/ICE/MAGMA/DESERT）的地形顆粒質感與改前是否一致；縮放到最大/最小看是否模糊。
4. 不要 push；合併進 `main`（= 發佈到 GitHub Pages）前先等主代理審查。
